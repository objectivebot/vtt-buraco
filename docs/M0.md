# M0 — feasibility / trust boundary

Status: experimental native VTT proof plus automated reference, importer, server,
and two-client relay tests. Browser E2E smoke tests are in
`tests/testcafe/m0.js`. Do not interpret any of these tests as server-side
enforcement of Buraco rules.

## Delivered architecture

- `scripts/game/table.mjs`: unchanged production Buraco table generator,
  isolated from build and archive I/O.
- `scripts/lib/vtt-archive.mjs`: deterministic VTT ZIP encoder, shared by
  production and the test table.
- `scripts/game/m0-probe.mjs`: isolated VTT-native test table, not mixed into
  the production game. One draggable card, two seats, source/target holders,
  a local authorization button and a destination enterRoutine which attempts
  to reject an unauthorized drop by returning the card to its origin.
- `src/core/prototype.mjs`: dependency-free reference reducer with explicit
  actor, expected revision (compare-and-swap), source/destination, immutable
  state transitions, event history and validated snapshot restore.
- `tests/upstream-m0-integration.mjs`: exercises real upstream Room.addState,
  two simulated clients, Room.receiveDelta and file persistence/reload.

The pure JS reducer is **not** called by the `.vtt`. It specifies expected
behavior for M1+ and lets us test the rules independently from UI behavior.

## Key upstream findings

1. `Holder.onChildAdd` executes `enterRoutine` on the client after the card
   arrives. A routine can locally send `SET child.parent = probeOrigin`.
   When an ordinary user moves a card, this is a useful best-effort UX guard.
2. The upstream `StateManaged.applyDelta` path simply applies received remote
   properties to client widgets; it does not run the local setter's
   propertyChangeRoutine or globalUpdateRoutine. The server's
   `Room.receiveDelta` merges incoming state, confirms it and broadcasts it.
   The M0 integration test demonstrates that a second client can submit an
   unauthorized parent change despite the local destination enterRoutine.
3. There is **no VTT-native authoritative, atomic rule engine** for arbitrary
   clients. A browser-side expected-revision counter cannot prevent a forged
   delta or guarantee linearizable moves across simultaneous clients.

**Decision for M1:** Native VTT controls are suitable for cooperative play
and for a guided interface, not enforceable cheating prevention. Treat
`src/core/prototype.mjs` as the trusted *specification*, not the deployed
engine. For strong guarantees, M1 would need a trusted server/proxy with a
server-side command API and authoritative snapshots (or an upstream server
extension). Do not claim otherwise.

## Manual two-browser acceptance test

1. Download `m0-probe.vtt` from the `main-build` prerelease or run
   `npm run build:probe`. Load it into a **new** VirtualTabletop room.
2. Open two browser profiles, use separate names (Alice and Bob), and occupy
   seats 1 and 2 respectively. Open the Active Game tab on both.
3. Without authorization, drag the ace from ORIGEM to DESTINO using Alice.
   Expected: local `enterRoutine` restores `probeOrigin`, and both clients
   eventually display the card at ORIGEM.
4. Bob presses the authorize button. Expected: the UI refuses; gate remains
   closed. Repeat the drag, which should still be rejected.
5. Alice presses Authorize and drags. Expected: the gate opens for one move,
   the card reaches DESTINO, both clients see the move, and the gate closes.
6. Reload Bob. Expected: the server's current card position and gate state
   are restored. Try an unauthorized second move after Reset.
7. Run the two-client scripted upstream test for the raw-delta case to see
   that server acceptance **is intentionally documented as a failed security
   boundary**, not a passing guarantee of enforceable game rules.

If steps 3–6 diverge, treat the native validation flow as not yet proven and
use only button-driven movements for future rule-dependent transitions.

## Scope boundary

M0 does not implement turn sequencing, combination validation, canastras,
eligibility for the morto, endgame or scorekeeping (M1–M7).
